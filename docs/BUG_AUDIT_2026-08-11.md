# Aezakmi Cafe — Bug Audit (pre-fix)

_Compiled Aug 11, 2026. This is a documentation-only pass — nothing in the
codebase has been changed yet. Each item below was traced to specific code so
we can fix them one at a time instead of guessing._

---

## 1. Customer app (`apps/customer`) — session start & Electron window

### 1.1 Window hides itself the instant a session becomes active (the "minimizes right after" bug)
- `CustomerSessionView.jsx` (effect around line 101-114) calls
  `window.aezakmiClient.activateSession(...)` as soon as `hasActiveSession`
  flips to `true`.
- That IPC call reaches `enterActiveState()` in
  `apps/customer/electron/main.cjs`, which immediately resizes the window to
  800×600 **and calls `mainWindow.hide()`** (`applyActiveWindowMode({show:false})`
  followed by `mainWindow.hide()`), with zero delay.
- Meanwhile `StartSessionModal.jsx` shows a "Session started ✔" confirmation
  and only calls `handleClose()` after a 900ms `setTimeout`.
- Net effect: the moment the backend confirms the session, the whole Electron
  window disappears into the tray — the confirmation message, and the "Start
  Session" screen itself, are yanked off-screen before the customer ever sees
  them. There is no visible transition from "fullscreen login/start screen"
  → "session confirmed" → "minimized dashboard"; it jumps straight to hidden.
- **Expected:** the window should stay visible (ideally still fullscreen or at
  least shown) long enough for the customer to see the session actually
  started, then transition to the 800×600 mini dashboard deliberately (e.g.
  after the confirmation timeout, or after an explicit "Continue" action) —
  not hide instantly on the same tick that `hasActiveSession` becomes true.

### 1.2 First-launch window is capped at 800×600 instead of true fullscreen
- `createWindow()` in `apps/customer/electron/main.cjs` constructs the
  `BrowserWindow` with `minWidth/maxWidth/minHeight/maxHeight` all locked to
  `ACTIVE_WIDTH`/`ACTIVE_HEIGHT` (800×600) **at the same time** it sets
  `kiosk:true` and `fullscreen:true`.
- Electron's fullscreen/kiosk implementation has to grow the window past
  800×600 on most displays; a hard `maxWidth`/`maxHeight` of 800×600 fights
  that, so on first startup the locked/login window can render at (or snap
  back to) 800×600 instead of covering the screen, or flash between sizes.
- `applyLockedWindowMode()` calls `setFullScreen(true)` again later, but it's
  operating on a window whose max bounds were already constrained at
  construction time, so the fix has to happen in the `BrowserWindow(...)`
  options themselves, not just in the mode-switch functions.
- **Expected:** the window should be created without a size cap (or created
  at full screen bounds) while locked, and only the *active* (logged-in +
  session-started) state should apply the 800×600 fixed size — the min/max
  constraints should be applied when entering active mode, not baked into
  window creation.

### 1.3 `applyActiveWindowMode` always resizes+hides, even for background/no-op calls
- `enterActiveState()` calls `applyActiveWindowMode({ show:false })` even
  when the window is already active (`if (isActive()) { applyActiveWindowMode({show:false}); ... return true }`).
  Every time `hasActiveSession` re-evaluates truthy (e.g. after any `refresh()`
  poll/socket event while a session is already active), this needlessly
  re-runs `setSize`/`center`, which can cause visible jitter if the mini
  dashboard is open at the time.
- This is downstream of 1.1: because `activateSession()` is called from a
  `useEffect` keyed only on session identity (`stateKey`), it *should* only
  fire once per session — but combined with 1.1 there's no visible "session
  starting" state in between, so any hiccup in that effect is invisible to
  the user until the window has already vanished.

### 1.4 No distinction between "session just started" and "app relaunched into an existing session"
- On a fresh Electron launch, `windowState` always starts at `LOCKED`
  (`app.whenReady()` hardcodes `windowState = WINDOW_STATES.LOCKED` and calls
  `applyLockedWindowMode()`), even if the renderer will immediately discover
  (via `/client/context` + auth restore) that a session is already active on
  this PC. That's arguably correct for security, but combined with 1.1 it
  means: launch → brief fullscreen flash → renderer detects active session →
  instant hide, with no readable UI in between. Worth deciding explicitly
  whether a relaunch mid-session should re-show the mini dashboard instead of
  silently hiding.

## 2. Admin app (`apps/admin`) — frontend bugs

> Several bugs from earlier passes are recorded as "fixed" in
> `ADMIN_FRONTEND_REVIEW.md` / `FRONTEND_BUTTON_AND_CUSTOMER_REVIEW.md`
> (Add Member button, Add PC id generation, Logs `entityType` field, inactive
> rate plans leaking into session UI). Those are not re-litigated here; the
> items below are newly identified in this pass.

### 2.1 Wallet balance changes made by one admin/cashier don't live-update other admin terminals
- `AppDataContext.jsx` (admin) listens for a `wallet:updated` socket event to
  patch a member's balance into local state without a full refetch.
- The backend's `emitWalletUpdated()` (`backend/src/realtime.js`) only emits
  to the `customer:${memberId}` room (`emitToCustomer`) — it never emits to
  the `admin`/`cashier` rooms.
- `POST /wallet/adjustments` (manual admin top-up/refund) calls
  **only** `emitWalletUpdated(...)`; it does **not** also call
  `emitDataChanged(...)`.
- Result: if two admin/cashier terminals are open, an admin who does a manual
  wallet adjustment on Terminal A sees the update locally (because
  `AppDataContext.adminTopUp/adminRefund` re-`refresh()`s after its own
  request resolves), but Terminal B never receives any realtime signal and
  will show a stale wallet balance until its next manual refresh or unrelated
  `data:changed` event.
- Same gap applies anywhere else `emitWalletUpdated` is called without a
  companion `emitDataChanged` (e.g. `/members/:id/wallet` set-balance,
  session refund, session extension paths) — worth auditing all six call
  sites in `apiRoutes.js`.

### 2.2 `AppDataContext.setMemberWallet` result depends on server echoing `balance`
- `setMemberWallet()` reads `data?.balance` from the `PATCH
  /members/:memberId/wallet` response to patch local state, but relies on
  optimistic local state only — it does not call `refresh()` afterward like
  every other mutator in this file does (`refreshAfter(...)`), so it's
  inconsistent with the rest of the module and won't pick up any other
  server-side side effects of that request (e.g. a linked session-time
  update).

*(Deeper component-level review — Floor Matrix, Members, Tariffs, Logs,
Settings pages — should happen alongside the fix pass; this file focuses on
what's already confirmed from source rather than a full line-by-line replay
of every component.)*

## 3. Backend — logic bugs / frontend↔backend mismatches

### 3.1 Session heartbeat interval is longer than the "stale" threshold
- Customer `AuthContext.jsx` sends `POST /auth/heartbeat` every **30
  seconds** (`setInterval(..., 30000)`), matching
  `backend/src/config/env.js`'s `heartbeatSeconds: 30` default.
- But `backend/src/utils/sessionTime.js#checkpointMemberSession` hardcodes
  `heartbeatStale = nowMs - lastHeartbeat > 25000` — **25 seconds** — and
  ignores the configured `heartbeatSeconds` value entirely.
- Because the heartbeat only fires every 30s, by the time the *next*
  heartbeat lands, the previous one is already >25s old, so the backend can
  routinely treat a perfectly healthy, currently-in-use station as
  "interrupted" (station offline) and freeze/checkpoint remaining time
  early — even though nothing is actually wrong. Some earlier docs
  (`BACKEND_SESSION_TIME_AND_TIER_REVIEW.md`) describe the heartbeat as
  running "every 10 seconds," which does not match the 30s interval actually
  in the code — the docs and the implementation have drifted apart.
- **Fix direction:** either shorten the heartbeat interval to comfortably
  clear the stale threshold (e.g. 10s heartbeat / 25s threshold, as the docs
  originally intended) or derive the stale threshold from
  `config.heartbeatSeconds` instead of a separate hardcoded constant, so the
  two can never drift again.

### 3.2 `data:changed` vs targeted events are inconsistently paired
- Some mutations emit both a targeted event (`session:updated`,
  `topup:updated`, etc.) **and** `emitDataChanged(...)` for a full
  admin/cashier refresh (e.g. member create/update, rate-plan CRUD,
  settings).
- Others (wallet adjustment, wallet set-balance, session refund/extension)
  emit only the targeted event, which — per 2.1 — doesn't reach staff rooms
  at all for wallet events. This means staff-side realtime freshness
  currently depends on which code path happened to remember to call
  `emitDataChanged`, rather than a consistent rule. Worth deciding one rule
  (e.g. "every state-mutating endpoint calls `emitDataChanged` in addition
  to any targeted event") and auditing every route against it.

### 3.3 Stale-session recovery only fires from the periodic sweep in `server.js`
- `server.js` has a periodic job that expires sessions whose `expires_at`
  has passed, using `last_heartbeat_at` to decide whether to trust
  `expires_at` or fall back to last-known remaining time. This is the same
  25s/30s mismatch as 3.1 — worth fixing in one place (`sessionTime.js`) since
  both `checkpointMemberSession` and the sweep in `server.js` need to agree
  on what "stale" means.

## 4. Suggested fix order

1. **1.1 + 1.2** (customer Electron) — highest visibility, matches exactly
   what was reported: window shouldn't disappear the instant a session
   starts, and shouldn't be boxed into 800×600 before the customer has even
   logged in.
2. **1.3 / 1.4** — cleanup once 1.1/1.2 are solid, to avoid regressions.
3. **3.1** (heartbeat/stale mismatch) — silent correctness bug that affects
   every active session, independent of UI.
4. **2.1 / 3.2** (admin realtime wallet gap) — visible mainly with multiple
   staff terminals open; lower urgency than the above but a real bug.
5. **2.2** — small consistency cleanup.

Once you confirm this list (or want anything added/removed/reprioritized),
we can start fixing in that order.
